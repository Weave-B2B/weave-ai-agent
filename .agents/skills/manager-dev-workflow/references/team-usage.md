# 팀에서 공유 개발 스킬 사용하기

이 묶음은 **개발을 돕는 Codex 서브에이전트**의 역할과 작업 절차다.
제품 서버에서 실행되는 AI 에이전트·API와는 별개이며 실행 중인 서버에 설치하는 기능이 아니다.
특정 제품 에이전트 번호나 작성자의 개인 스킬 폴더에 의존하지 않는다.

## 준비

저장소의 `.agents/skills/manager-dev-workflow/`, `.codex/agents/`,
`docs/dev-workflow/project.json`, `AGENTS.md`를 함께 공유한다.
동료는 자신의 체크아웃에서 **대상 저장소 루트**를 열고 사용한다.
로컬 파일만 수정한 상태라면 팀 저장소에 커밋·PR로 반영한 후 동료가 받아야 한다.
스킬 사용 자체가 커밋·push·배포 허가는 아니다.

별도의 개인 스킬 설치나 작성자의 절대 경로는 필요하지 않다.
Notion·Figma 접근 권한, 모델 API 키는 각자의 환경에서 준비한다.
연결이 없으면 접근 가능한 문서나 로컬 자료를 요청하며, 읽지 못한 자료를 확인했다고 하지 않는다.
현재 세션에 실제 서브에이전트 실행 도구가 있어야 분리 실행할 수 있다.
없으면 한 에이전트가 역할 순서대로 처리하는 대안을 설명하고 사용자의 선택을 받는다.

## 호출

스킬 선택기에서 `manager-dev-workflow`를 선택하거나 다음처럼 요청한다.

```text
$manager-dev-workflow
대상: [개발할 제품 에이전트 또는 기능 이름]
요청: [추가하거나 수정할 동작]
기존 기획/설계: [문서 링크 또는 저장소 상대 경로]
이번 범위: [서버/API/화면 중 필요한 부분]
완료 기준: [확인할 입력과 기대 결과]
필요한 역할만 선택하고 각 담당자는 내 답변을 받은 뒤 시작해줘.
```

이름으로 선택되지 않으면 아래처럼 파일을 직접 지정한다.

```text
.agents/skills/manager-dev-workflow/SKILL.md를 읽고 이번 작업에 적용해줘.
대상과 범위는 아래 요청을 기준으로 정하고 이전 작업 범위를 이어받지 마.
```

역할이 선택 도구에 없으면 매니저가 저장소의 역할 TOML을 읽어 실제 서브에이전트에
지시로 전달할 수 있다. 파일이 존재하는 것과 클라이언트가 역할을 등록한 것은 구분한다.

직접 한 번 수정하고 싶을 때는 다음처럼 요청하면 된다.

```text
매니저 스킬과 서브에이전트를 사용하지 말고 이 파일만 직접 수정해줘: [경로와 변경 내용]
```

## 작업에 맞게 역할 고르기

| 요청 | 주로 필요한 역할 |
|---|---|
| 새 서비스 또는 요구가 부족한 기능 | 자료 조사·기획 후 필요한 구현 담당과 QA |
| 기획이 있는 제품 에이전트 개발 | 해당 에이전트/API 담당과 QA. 빠진 계약만 조사 |
| 기존 API에 화면 연결 | 필요한 계약 확인, 화면 담당, UI/API QA |
| 작은 서버 기능 추가 | 해당 서버 담당과 관련 QA. 불필요한 화면·DB 작업 생략 |
| 문서 수정·읽기 검토 | 해당 업무만 수행. 전체 개발팀을 자동 실행하지 않음 |

`workflow-domain`은 지정한 제품 에이전트·백엔드/API·도구를 구현하고,
`workflow-prototype`은 지정한 화면을 담당한다. `workflow-sources`는 자료 조사,
`workflow-planner`는 요구와 완료 기준 정리, `workflow-qa`는 독립 검증을 맡는다.
메인 채팅이 매니저를 맡으므로 `workflow-manager`를 추가 실행할 필요는 없다.
별도 데이터·보안·인프라 전문 작업이 필요하면 해당 역할의 가용성과 추가 범위를 먼저 확인한다.

## 작업 프로필과 수정 경로

기본 프로젝트 정보는 `docs/dev-workflow/project.json`에서 읽는다.
매 작업에서 대상 에이전트/기능, 정확한 수정 경로, 소스, 완료 기준, 관련 검사를 정한다.
`ownership`에 적힌 넓은 경로는 역할 후보 영역이며 전체 수정 승인이 아니다.
동시에 같은 파일을 두 담당자가 수정하지 않게 작업별 소유자를 정한다.

반복 사용할 특별한 범위가 있으면 `docs/dev-workflow/profiles/<작업명>.json`에
작업 프로필을 두고 **호출할 때 경로를 명시**한다. 모든 경로는 프로필 위치와 무관하게
저장소 루트 기준이다. 지정된 프로필의 최상위 항목은 기본 프로필의 같은 항목을
대체하고, 없는 항목은 기본값을 따른다. 하위 배열을 자동 합치지 않는다.
이는 매니저의 해석 규칙이며 별도 설정 병합 엔진이 실행되는 것은 아니다.
작업 프로필은 사용자 승인이나 저장소 규칙을 대신하지 못한다.

실행 기록은 `docs/dev-workflow/runs/<새 run-id>/`에 남긴다.
`run.json`에 사용한 프로필과 대상·허용 경로·완료 기준·검사 명령을 기록한다.
이전 run은 이력이며 새 요청의 대상이나 제외 범위로 자동 적용하지 않는다.
특정 에이전트의 전용 테스트나 PM 승인 API를 다른 에이전트의 공통 조건으로 쓰지 않는다.

## 승인과 QA

기본 절차는 필요한 역할 선택 → 담당자의 쉬운 착수 설명 → 사용자 답변 → 구현·인수인계
→ 별도 QA다. 필요한 정보는 매니저가 조사 담당이나 사용자에게 연결한다.
이미 기획이 있으면 전체 기획을 다시 만들지 않는다.
특정 담당과 범위를 묶어서 승인했다면 같은 일을 반복 승인받지 않는다.

QA는 실제 최종 코드와 완료 기준을 비교하고 발견한 문제를 담당자에게 돌려보낸다.
새 수정·재검증은 승인 범위를 확인하며 기본 최대 두 회다.
QA가 제품 코드를 직접 고쳐 통과시키지 않는다. 승인되지 않은 추가 작업이나
필수 정보 부족은 대기 상태로 보고한다. 개발 착수 승인과 제품 내부의 PM·고객 승인은 별개다.

보고할 때 설정 검사·자동 테스트·브라우저 확인·mock API·실제 모델 호출을 구분한다.
외부 모델 호출이 필요하면 키·비용·허가 범위를 확인하고 키를 문서나 Git에 저장하지 않는다.

## 다른 프로젝트로 가져가기

Python 3.11 이상을 사용하고 이미 존재하는 대상 폴더를 지정한다.
아래 명령은 이 묶음을 가진 저장소 루트에서 실행한다. 대상 경로는 본인의 경로로 바꾼다.

```bash
python .agents/skills/manager-dev-workflow/scripts/bootstrap.py --target /path/to/new-project --dry-run
python .agents/skills/manager-dev-workflow/scripts/bootstrap.py --target /path/to/new-project
```

스킬 전체·역할 6개·빈 기본 프로필·AGENTS 안내를 설치한다. 기존 프로필과 규칙을 보존하고,
다른 내용의 파일이 충돌하면 덮어쓰지 않고 중단한다. 기존 설치를 자동 업그레이드하는 도구는 아니다.
현재 프로젝트의 작업 프로필·Notion/Figma 링크·run 기록은 복사하지 않는다.
설치 후 대상 `project.json`의 소유 경계와 소스를 채운다. 설치만으로 개발팀이나 서버가 실행되지는 않는다.

설치 도구를 변경하거나 설치 동작을 확인할 때는 다음 검사를 사용할 수 있다.

```bash
python -m unittest discover -s .agents/skills/manager-dev-workflow/scripts/tests -v
```

이 검사는 설치 동작을 확인하며 제품 기능이나 실제 멀티에이전트 실행 품질을 증명하지 않는다.
