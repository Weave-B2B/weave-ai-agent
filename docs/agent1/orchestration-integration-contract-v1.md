# Agent 1 오케스트레이션 연동 계약 v1

## 의도 및 항목 규칙

- 항목 분리가 식별 기준이다. 항목마다 하나의 `intent`를 사용하며 `intents` 목록을 사용하지 않는다.
- 확인 의도와 변경 작업 의도가 한 항목에 섞이면 항목을 나눈다.
- 항목을 다시 나눌 때 변경되지 않은 항목의 ID는 유지한다. 새 항목 또는 실제로 분리된 항목에만 새 ID를 부여한다.
- `change_request`, `confirmation`, `defect`, `issue_report`는 범위 판단 대상 후보이다.
- `status_check`와 빈 항목 목록은 Agent 2를 호출하지 않는다.
- 기능이나 문서 대상이 언급됐는데 의도가 애매하면 `status_check`가 아니라 `confirmation`으로 분류한다.

## 견적 의도 차이

- `estimate_only`: 변경 요청 없이 이미 지정된 항목이나 기존 범위의 가격만 묻는 의도이다. 자동으로 `estimate_request`로 변환하지 않는다.
- `estimate_request`: 변경 대상 항목과 연결되는 별도의 명시적 견적 요청이다. 하나 이상의 대상 항목 ID에 연결하며 중복 산정을 만들지 않는다.
- 의미가 확정되지 않은 경우에는 `estimate_request` 문의를 유지하거나 `NEEDS_INPUT`을 반환한다. 한 의도를 다른 의도로 추정해서 바꾸지 않는다.

## 조건부 후속 요청

공통 `Item`과 내부 초안 모델은 선택 필드 `conditional_followup` 문자열을 지원한다. 이 필드는 다음과 같은 원문상 명시적 표현만 보존한다.

```text
포함인지 확인하고, 안 되면 추가해주세요.
```

Agent 2는 확인 항목의 범위를 판단할 수 있다. 판정이 검증된 `out_of_scope`이고 항목에 `conditional_followup`가 있으면 호스트는 확인 항목을 잠정 변경 대상으로 전환한 뒤 산정할 수 있다. 최종 승인 절차는 계속 PM 최종 검토이며 원래 항목은 이력으로 남는다.

## 확인 항목 Assembly

확인 항목 정규화는 항목의 근거(`text`, `quotes`)를 기준으로 수행한다. 메일에 확인 표현이 있다는 이유만으로 모든 function 항목을 확인 항목으로 변환하지 않는다. 확인 의도와 변경 의도가 섞인 메일은 각각 별도 항목과 원래 의도를 유지한다.

## 재호출 동작

- `resplit`: 요청된 대상 항목 ID만 다시 분리한다. 변경되지 않은 항목의 ID는 유지한다.
- `analyze_answer`: 답변과 연결된 변경 항목 또는 질문만 갱신한다. 관계없는 열린 질문은 삭제하지 않는다.
- 답변 이벤트가 추가됐다는 이유만으로 답변 분석이 질문을 해소 처리하지 않는다. 해소 여부는 해석된 내용과 재실행 결과를 기준으로 판단한다.

## 부족 정보와 잠정 흐름

범위 판단 대상 항목이 남아 있는 경우 Agent 1의 `NEEDS_INPUT`은 오케스트레이션을 멈추는 이유가 아니다. 이는 공통 질문 목록의 미해결 입력을 나타낼 뿐이며 잠정 항목을 Agent 2가 처리하는 것을 막지 않는다. PM 또는 고객 대상 블로킹 질문은 계속 표시되며 자동 승인 기록이나 해소 상태로 변경하지 않는다.
