# 엑셀 단가표 등록과 프로젝트 영향 산정 연결 계획

작성일: 2026-11-20. 갱신: 2026-11-21. 상태: **로컬 구현 및 회귀 검증 진행**. 백엔드 등록·Run 연결·프로토타입 검토 기능을 구현했다. 실제 모델을 사용한 두 서버 전체 브라우저 E2E와 배포 검증은 별도로 남아 있다. 아래 설계와 마지막 보완 결과를 구분해서 읽는다.

범위 수정: 실제 프론트엔드의 영향 산정 화면 디자인이 완료되지 않았으므로 **이번 작업에서는 `weave-frontend`를 수정하지 않는다.** 백엔드·AI 서버 연동을 API로 먼저 검증하고, AI 서버의 로컬 프로토타입을 검증용 화면으로 연결한다. 실제 서비스 화면 연결은 디자인 확정 후 후속 작업으로 분리하며, 삭제된 `?live=1` 경로를 복원하지 않는다.

## 1. 목표와 사용자 흐름

같은 엑셀의 WBS·인력·휴무는 일정 자료로, 단가표는 프로젝트의 공식 단가표 등록 입력으로 사용한다. 금액 계산식은 기존 백엔드 계산기 한 곳에 유지한다.

다음은 AI 서버 프로토타입에 추가할 검증 흐름이다. 기존 서비스 화면의 완성 여부와 독립적으로 진행한다.

1. 실제 백엔드에 등록된 테스트 프로젝트를 선택하고, `일정·공수 자료`로 XLSX를 업로드한다. 프로토타입 업로드도 기존 백엔드 파일/문서 API와 저장소를 사용한다.
2. 업로드된 **문서 버전**에서 단가표를 읽어, 현재 등록값과 새 값을 나란히 보여준다.
3. 처음 등록하거나 단가가 달라졌으면 등록 권한이 있는 사용자가 **프로젝트 단가표로 등록**을 누른다.
4. 백엔드에 공식 단가표 버전을 저장한다. 적용일이 미래라면 예약 상태로 안내한다.
5. 변경 요청 영향 산정 시 프로젝트의 현재 유효한 단가표 UUID를 확정해 Agent 3에 전달한다.
6. Agent 3이 만든 작업·공수를 기존 계산 API로 계산하고, 사용한 단가표 버전과 엑셀 출처를 결과에 표시한다.

파일을 올렸다는 사실만으로 단가를 바꾸지 않는다. 주간 진행률만 바꿔 재업로드하면 단가가 같다는 안내만 표시하고 새 단가 버전을 만들지 않는다. 일정 자료 승인과 단가 등록은 기존 권한이 다르므로 별도 선택으로 둔다.

위 흐름을 프로토타입 검증 페이지에 연결했다. 기존 사용자 인증을 사용하는 백엔드 전달 계층이며 가상 JSON 단가 저장과 구분한다. 향후 실제 서비스 화면에서도 같은 백엔드 계약을 사용한다.

## 2. 착수 당시 구현과 보완 범위

| 영역 | 현재 코드 | 추가 작업 |
|---|---|---|
| 파일 업로드 | `IMPACT_WORKBOOK`, XLSX 10MB, 프로젝트 소속·문서 버전 관리 | 등록된 원본에서 단가표 추출 |
| 일정 자료 사용 | 승인·적용일 조건으로 최신 자료 조회, Agent 3이 일정 입력으로 사용 | 기존 경로 유지, 단가 등록 상태와 구분 |
| 단가표 등록 | `RateCardService.create`, 회사 ADMIN 검사, 프로젝트별 버전·직군 단가 저장 | 엑셀 미리보기·확인 등록을 이 서비스에 연결 |
| 단가표 제약 | 프로젝트 통화 일치, 회사 직군 ID 확인, PM·UX·FE·BE·QA 모두 필요 | 엑셀 코드 → 회사 직군 UUID 매핑 |
| Agent 3 단독 실행 | `ImpactAnalysisService`가 프로젝트의 현재 단가표 UUID를 선택 | 새 등록값이 선택되는지 통합 검증 |
| 통합 Supervisor 진입 | `OrchestrationBridgeService`가 단가 미지정 시 `RC-SYNTH-2026H2-v1` 사용 | 실제 프로젝트 현재 단가표로 변경. 없으면 등록 안내로 중단 |
| 기존 Run 재호출 | `RunStateService.create`는 최초 `rate_card_id`를 한 번만 저장 | 단가 변경은 명시적 재산정 입력 리비전으로 반영 |
| 금액 계산 | `EstimateCalculationService`가 프로젝트에 속한 단가표 UUID로 계산 | 유지. 엑셀 가격을 계산 API의 임의 행 단가로 직접 전달하지 않음 |
| 승인 검증 | 저장된 단가 스냅샷·정책·금액 재검증 존재 | 프로젝트의 새 유효 단가표로 바뀐 미승인 결과 감지 추가 |

`STORED`는 원본 저장 완료이지 단가 검증·등록 완료가 아니다. 현재 엑셀 단가 시트는 일정 파서와 LLM에 전달되지 않는다.

## 3. 엑셀에서 읽는 항목

| 위치 | 의미 | 처리 |
|---|---|---|
| `단가표!B4` | 단가 적용 시작일 | 필수 날짜. 문서의 일정 자료 적용일·WBS 진행률 기준일과 별도 |
| `단가표!B5` | 1MD 기준 시간 | 현재 양식은 `인력 투입 계획!B4`를 참조하는 수식 |
| `단가표!B6` | 통화 | 프로젝트 통화와 일치하는 대문자 3자리 코드 |
| `단가표!A9:A13` | 직군 코드 | PM·UX·FE·BE·QA, 각각 한 번씩 필요 |
| `단가표!B9:B13` | 직군명 | 화면 설명용. UUID 매핑은 A열 코드로 수행 |
| `단가표!C9:D13` | 내부 원가·판매 단가 | 부가세 제외 1MD 금액, 0 이상 Decimal. 빈칸은 오류, 명시적 0은 별도 확인 |
| `단가표!E9:E13` | 비고 | 참고용. 가격 결정이나 직군 식별에 사용하지 않음 |

- 단가가 없는 기존 엑셀은 계속 일정 자료로 사용할 수 있다. 현재 프로젝트 단가표가 있으면 그대로 사용한다.
- 다섯 직군 코드 중복·누락·미지원 코드·회사에 없는 직군은 행/셀 위치와 함께 안내한다. 직군을 임의 생성하지 않는다.
- DB 금액의 정밀도·범위를 적용하고 부동소수점 반올림으로 입력값을 바꾸지 않는다. 가격 합계 행은 만들지 않는다.
- 1MD 시간은 `0 < 시간 <= 24`이며 선택한 공식 단가표와 일정 입력의 기준 시간이 같아야 한다.
- B5는 허용된 정확한 내부 참조만 확인하고, 참조 대상의 숫자를 서버가 읽는다. 임의 수식 실행이나 오래된 수식 캐시값에 의존하지 않는다. 나머지 등록 입력은 상수값만 허용한다.
- 예시 가격은 `RC-SYNTH-2026H2-v2`의 합성 값이다. 실제 프로젝트 등록값으로 간주하지 않는다.

## 4. 서버 책임과 등록 경계

### 백엔드

- `ObjectStorage.readObject`와 문서/파일 메타데이터를 이용해 해당 프로젝트의 업로드 완료 원본을 읽는다. 파일 크기·SHA-256을 실제 바이트로 재확인한다.
- XLSX 전용 결정론적 파서를 추가한다. 현재 백엔드에는 엑셀 파서 의존성이 없으므로 파서 라이브러리 도입과 압축/XML 크기 제한이 필요하다. 외부 연결·매크로·임의 수식은 실행하지 않는다.
- 단가표 추출·검증·직군 매핑을 수행한다. AI 서버나 LLM의 가용성 없이 등록할 수 있게 한다.
- 저장은 기존 `RateCardService`의 검증·프로젝트 잠금·버전 발급 로직을 재사용한다. 같은 DB에 가격을 따로 보관하는 공식 계산 엔진을 추가하지 않는다.

### AI 서버

- 기존 WBS 파싱과 작업 분해·공수 산정을 유지한다.
- 등록된 단가표 UUID와 실제 프로젝트 UUID로 기존 금액 계산 API를 호출한다.
- 엑셀의 원가·판매 단가를 프롬프트나 RAG에 넣지 않는다. API 오류 시 합성 단가로 대체하지 않는다.
- 이 작업은 전송 방식(HTTP/SQS)을 바꾸지 않는다. 같은 UUID를 실행 입력에 전달하는 경계만 맞춘다.

### 검증용 화면 — AI 서버 프로토타입

- `prototype/app.js`·`prototype/api.js`·`prototype/analysis-demo.js` 등 실제 진입 구조를 확인해 로컬 검증용 화면을 추가한다. 공식 프론트의 파일·메뉴·디자인은 수정하지 않는다.
- 실제 테스트 프로젝트 선택 → 엑셀 업로드 → 단가표 미리보기/확인 등록 → 해당 변경 요청 영향 산정 순서로 연결한다.
- 현재값과 업로드값, 적용 시작일, 등록 후 버전을 보여준다. 가격이 같으면 `기존 단가표와 동일`로 표시한다.
- 기존 단가 등록 권한(회사 ADMIN)과 프로젝트/파일 접근 권한을 서버에서 검사한다. PM의 일정 자료 승인만으로 ADMIN 권한을 대신하지 않는다.
- PM에게 등록 권한이 없으면 일정 자료는 기존 절차로 저장할 수 있고, 단가 등록은 관리자 확인 필요로 표시한다. 새 단가 미등록 상태를 숨기고 그 가격으로 산정했다고 표시하지 않는다.
- 기존 `prototype/rate_routes.py`의 저장 경로는 `.prototype-rate-cards`에 `RC-LOCAL-*` JSON을 만드는 로컬 테스트 기능이다. 이를 공식 프로젝트 단가 등록으로 표시하거나 사용하지 않는다. 이번 실연동 모드는 백엔드 등록 API가 발급한 UUID를 사용한다.
- `app/api/local_run_routes.py`는 로컬 SQLite와 백엔드 저장을 모두 지원하므로, 실연동 검증에서는 **백엔드 연결 모드**를 명확히 확인한다. 실제 프로젝트·변경 요청·행위자 UUID가 없으면 중단하고 합성 ID나 SQLite로 자동 전환하지 않는다.
- 백엔드 사용자 API는 정상 로그인 자격과 회사/프로젝트 컨텍스트로 호출한다. 로컬 어댑터가 필요하면 얇은 전달 계층만 두고, 서비스 토큰으로 ADMIN 권한을 우회하지 않는다. 내부 서비스 토큰은 브라우저 코드에 넣지 않는다.
- 화면에 `실제 백엔드 DB 연결` 여부, 선택한 프로젝트, 사용 단가 UUID/버전, 원본 문서 버전을 표시한다. 가상 데이터 모드와 실연동 모드의 검증 결과를 구분한다.

### 실제 서비스 프론트엔드 — 후속 작업

- 화면 디자인 확정 후 `weave-frontend`의 문서 업로드/영향 산정 화면에서 위 백엔드 계약을 호출한다.
- 프로토타입의 화면 코드를 복사하거나 삭제된 Live 앱을 복구할 필요는 없다. API·DTO·테스트 시나리오를 재사용하고 최종 디자인에 맞게 표현한다.
- 이번 단계의 완료 조건에 실제 서비스 화면 연결이나 배포 환경 UI 검증을 포함하지 않는다.

## 5. API 계약 초안 — 신규 제안과 기존 API 구분

| 구분 | 경로 | 용도 |
|---|---|---|
| 기존 | `GET /api/v1/job-roles` | 회사 직군 코드와 UUID 확인 |
| 기존 | `POST /api/v1/projects/{projectId}/rate-cards` | 공식 단가표 버전 생성. 등록 로직 재사용 |
| 기존 | `GET /api/v1/projects/{projectId}/rate-cards/current` | 현재 유효 단가표 확인 |
| 신규 제안 | `POST /api/v1/projects/{projectId}/rate-card-imports/preview` | 문서 버전 원본에서 추출·오류·현재값과 차이 조회 |
| 신규 제안 | `POST /api/v1/projects/{projectId}/rate-card-imports/confirm` | 검토한 동일 원본을 확인하고 등록/기존 버전 재사용 |

미리보기 입력은 `documentVersionId`이다. 응답에 `sourceSha256`, 정규화한 `normalizedInputHash`, `currentRateCardVersionId`(없으면 null), 적용일·통화·시간·직군별 차이·셀별 오류를 포함한다. 오류가 있으면 등록할 수 없다.

확인 요청은 위 원본 버전/해시와 `expectedCurrentRateCardVersionId`, `operationId`를 보낸다. 서버가 원본을 다시 확인하며, 브라우저가 보낸 가격 자체를 신뢰해 저장하지 않는다. 현재 단가가 미리보기 후 바뀌면 409로 재확인을 요청한다. 응답은 `REGISTERED`/`UNCHANGED`/`SCHEDULED`와 실제 `rateCardVersionId`/버전/적용일이다. 미래 적용일이어도 신규 버전은 저장하되 현재 사용 중인 표와 구분한다.

미리보기/확인 등록 경로는 현재 로컬 작업 트리에 구현되어 있다. 계산·단가 조회는 기존 API를 사용한다.

## 6. 재업로드·중복 방지·저장

- WBS 내용이나 파일 저장 시각을 제외하고 **적용일·통화·1MD 시간·직군별 원가/판매 단가**만 정렬·정규화해 비교한다. 가격의 650000과 650000.00은 동일하게 본다.
- 같은 프로젝트에서 같은 단가를 다시 올리면 기존 단가 버전을 연결한다. 같은 파일명이라고 같은 파일로 판단하지 않는다.
- 별도 등록 이력(테이블 추가 제안)에 프로젝트·회사·원본 문서 버전·실제 파일 해시·정규화 해시·등록된 단가 UUID·작업 ID·등록자·시각을 남긴다. 하나의 단가 버전에 여러 주간 자료 출처를 연결할 수 있다.
- 멱등 키와 프로젝트 잠금 아래에서 중복 등록을 방지한다. 단가 버전 생성과 이력 저장은 같은 트랜잭션으로 처리한다.
- 문서 업로드 성공 후 단가 등록이 실패하면 파일은 남고 단가는 바뀌지 않는다. 화면에서 단가 등록만 다시 시도한다.
- 전체를 빈칸으로 둔 단가 시트는 `미작성`, 일부만 입력했거나 잘못된 값은 `오류`로 구분한다. 기존 프로젝트는 사용자가 **기존 단가표 유지**를 선택할 수 있다. 단가표가 없는 새 프로젝트는 등록 전 금액 산정을 막는다.

## 7. Agent 3 단독·Supervisor·재산정 통일

1. **새 분석 시작**: 백엔드가 한국 날짜 기준으로 현재 유효한 프로젝트 단가표를 선택한다. Supervisor의 합성 기본값을 제거한다. 외부에서 UUID를 명시했어도 프로젝트 소속·적용 가능 여부를 검증한다.
2. **실행 중 고정**: 단가표 UUID와 원본 엑셀 버전/해시를 실행 컨텍스트에 고정한다. 에이전트·도구가 호출될 때마다 다른 최신 가격으로 조용히 바꾸지 않는다.
3. **기존 Run 재사용**: `create`를 다시 호출해 새 UUID를 보내는 방식은 최초 입력 보존 때문에 반영되지 않는다. 기존 Run 입력/재산정 경로에 **계산 컨텍스트 리비전**을 추가하는 초안을 먼저 확정한다. `rate_card_id`, 엑셀 원본 버전/해시, 변경자·사유·기대 상태 리비전을 기록하고, AI `RunInputs` 조회는 이 최신 컨텍스트를 사용하게 한다. 최초 입력은 이력으로 보존한다.
4. **단가 변경 후 재산정**: 새 유효 단가표로 바뀐 미승인 분석은 재산정 필요로 표시하고 기존 금액·초안의 최종 승인을 막는다. `새 단가표로 재산정` 한 번으로 총괄이 재개되어 필요한 Agent 3·문서 생성만 다시 수행하게 한다. Agent 1·2는 관련 입력이 그대로면 재사용한다.
5. **기존 확정 결과**: 확정된 견적 라인·전달된 협의안·승인 이력을 수정하지 않는다. 새 검토/재산정 버전에서 금액·초안을 만들고 다시 승인받는다.
6. **미래 적용일**: 적용 전에는 기존 유효 표를 사용한다. 새 표가 유효해지는 날짜 이후의 실행·최종 검토에서 변경 여부를 확인한다. 첫 표가 미래 적용이고 현재 표가 없으면 금액 산정은 보류한다.
7. **승인 시 확인**: 원본·단가·정책·입력 리비전이 계산 스냅샷과 일치하는지 확인한다. 현재 `assertCurrent`는 정책 확인 중심이므로, 새 유효 단가표와의 비교를 추가할 지점도 검증한다. 자료가 변경되면 재산정 안내로 전환하며 모델 재시도를 반복하지 않는다.

`calculation_context_revision`과 전용 입력 갱신 경로는 `RunInputsView`·AI `RunInputs` 및 통합 DTO 문서에 반영했다. 상태 변경은 먼저 커밋하며, AI HTTP 실행은 트랜잭션 밖에서 호출한다.

## 8. 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 백엔드 엑셀 추출·직군 매핑·미리보기 | 다섯 직군 가격·적용일·통화·시간을 원본과 동일하게 읽고 잘못된 셀을 안내 |
| 2 | 확인 등록·출처 이력·중복 방지 | 같은 단가 재업로드 시 버전이 늘지 않고 새 가격은 새 공식 버전으로 저장 |
| 3 | 단독·Supervisor의 단가 선택 통일 | 합성 기본값 없이 같은 프로젝트의 같은 공식 단가 UUID로 산정 |
| 4 | Run 컨텍스트 갱신·초안 무효화·재승인 | 기존 Run에서도 새 단가가 실제 적용되고 오래된 금액·초안 승인은 차단 |
| 5 | 실제 DB·계산 API 통합 검증 | 프로젝트 생성 → 엑셀 등록 → 단가 확인 등록 → 영향 산정 → 검토·저장을 화면 없이 검증 |
| 6 | AI 서버 프로토타입 연결·브라우저 검증 | 실제 백엔드 DB와 같은 API를 사용해 업로드부터 재산정까지 화면에서 재현 |
| 후속 | 디자인 확정 후 실제 프론트 연결 | 최종 서비스 화면에서 같은 계약으로 호출. 이번 구현 범위 제외 |

작업 3의 신규 실행 연결은 1·2와 병행 준비할 수 있다. 백엔드·AI 서버 연결 완료는 5 통과 후, 프로토타입 화면 검증 완료는 6 통과 후 별도로 안내한다. 실제 서비스 화면 연결 완료와 혼동하지 않는다.

## 9. 검증 시나리오

- 정상: 새 프로젝트에 모노마켓 예시 가격을 등록하고, Agent 3 단독·Supervisor에서 등록 UUID/시간/가격이 모두 같게 전달되는지 확인한다.
- 변경: 예시의 BE 판매 단가를 700,000 → 750,000으로 바꾸면 BE 2.5MD의 **인건비 판매가 부분**이 125,000 증가한다. 경비·할인·VAT를 포함한 최종값은 기존 계산 정책으로 별도 검증한다.
- 중복: WBS 진행률만 수정한 파일 재업로드, 같은 등록 버튼 두 번 클릭, 동시에 확인 등록, 응답 유실 후 재시도 모두 단가 중복 버전을 만들지 않는다.
- 누락/오류: 단가 시트 없음·전체 미작성·부분 미작성·명시적 0·음수·소수 정밀도 초과·직군 중복/누락·다른 통화·날짜 오류·임의 수식·MD 시간 불일치를 구분한다.
- 원본/권한: 다른 프로젝트 파일, 바뀐 파일 해시, 미완료 업로드, 관리자 권한 없음, 미리보기 후 다른 사용자가 단가를 바꾼 경우 등록을 막는다.
- 적용일: 미래 표 등록 직후와 적용 당일, 유효 표 없음, 문서 적용일과 단가 적용일이 다른 경우를 확인한다.
- 재산정: 기존 Run 최초 입력이 남아 있어도 최신 계산 컨텍스트로 Agent 3이 다시 계산하고 새 초안을 생성하는지 확인한다. 실행 중 가격 변경·오래된 승인 요청도 포함한다.
- 보호: PM이 수정한 라인 및 확정 견적을 재업로드가 덮어쓰지 않는다. 기존 협의안/승인 이력과 원본 파일을 보존한다.
- 분리: 엑셀 단가를 임베딩·Agent 2·LLM 컨텍스트로 보내지 않고, 실패 시 합성 가격으로 대체하지 않는다.
- 프로토타입 실연동: 실제 프로젝트·변경 요청·단가표 UUID와 DB 등록 결과를 확인한다. `RC-LOCAL-*` 생성 또는 로컬 SQLite 저장만 성공한 것은 백엔드 연결 성공으로 인정하지 않는다. 공식 프론트의 미완성 화면 없이도 이 절차를 검증한다.

## 10. 2026-11-21 검토 후 보완

- **트랜잭션 경계**: Supervisor 시작·재산정은 외부 트랜잭션도 중단(`NOT_SUPPORTED`)한 상태로 실행한다. 계산 컨텍스트 갱신 서비스의 커밋이 끝난 다음 AI가 같은 리비전을 읽게 했다. Spring AOP 트랜잭션 테스트에서 외부 트랜잭션이 있어도 AI 호출 전에 내부 변경이 커밋되는지 검증한다.
- **입력 우회 차단**: 일반 `/inputs` DTO에서 `CALCULATION_CONTEXT`를 허용하지 않는다. 전용 경로가 현재 단가/원본을 검사하고 실행 중 컨텍스트 변경을 차단한다.
- **원본 고정**: Run 컨텍스트를 Agent 3에 전달하며, 원본 버전·해시 또는 원본 없음이 바뀌면 S3 읽기와 모델 호출 전에 중단한다. 컨텍스트가 변경된 재산정은 전체 산정 대상을 다시 계산한다. 과거 결과/원본은 이력으로 남긴다.
- **안전한 표시**: 업로드 파일명·엑셀 검증 오류·직군명·문서 초안을 HTML로 실행하지 않고 텍스트로 표시한다. 상세 JSON도 이스케이프한다.
- **PM 상호작용**: 프로토타입에서 선택지 클릭 또는 기타 입력으로 답변하고, 백엔드가 다음 작업까지 자동 실행한다. 최종 승인·보류·반려와 보류 해제도 연결했다. 최종 검토 번들은 브라우저가 보내지 않고 백엔드가 현재 서버 번들과 기대 리비전을 확인한다.

추가 사용자 API(기존 `orchestrations` 경로 아래):

| 메서드·하위 경로 | 요청 | 처리 |
|---|---|---|
| `GET /status` | 없음 | 현재 질문·초안·리비전 조회 |
| `POST /answers` | `expectedStateRevision`, `operationId`, `questionId`, `answer`, `disposition` | 답변 저장 후 실행 가능한 상태면 총괄 자동 재개 |
| `POST /final-review` | `expectedStateRevision`, `operationId`, `decision: approve/hold/reject` | 현재 서버 검토 번들로 검증/승인. 클라이언트 번들은 사용하지 않음 |
| `POST /resume` | `expectedStateRevision`, `operationId` | 보류 해제 후 총괄 자동 재개 |

새 사용자 API의 전체 접두사는 `/api/v1/projects/{projectId}/change-requests/{changeRequestId}/orchestrations`이다. 원본 조회는 프로젝트 공개 Facade와 DTO를 거쳐 다른 파트의 내부 서비스에 직접 의존하지 않는다.

프로토타입: `http://127.0.0.1:8000/prototype/workbook-rate-card.html`. `PROTOTYPE_LAB=1`이 필요하며 사용자 JWT 또는 기존 백엔드 local 프로필 인증을 전달한다. 단가 등록 권한과 프로젝트 PM/검토 권한은 각각 서버가 검사한다.

검증은 서로 구분한다. 실제 PostgreSQL 테스트는 등록·계산·출처 검증·컨텍스트 저장을 확인하고, 브라우저 UI 테스트는 HTTP 응답을 모의해 업로드 → 미리보기 → 등록 → 선택지/기타 답변 → 보류 → 재개 → 최종 승인 동작을 확인한다. 이 두 검증을 실제 모델까지 연결한 전체 E2E 통과로 표현하지 않는다.
