# 일정·공수 엑셀 업로드와 Agent 3 연결

작성일: 2026-11-19. 2026-11-20 갱신: 엑셀 기반 일정 계산(schedule-v1) 연결, WBS·인력 투입 계획 양식(wbs-v1) 추가. 규칙은 [schedule-calculator.md](schedule-calculator.md).

단가 시트를 공식 프로젝트 단가표로 등록하고 단독/통합 영향 산정에 연결하는 작업은 [엑셀 단가표 연결 계획과 보완 결과](workbook-rate-card-integration-plan.md)에 정리했다. 2026-11-21 로컬 작업 트리에 백엔드 등록·AI 연결·검증용 프로토타입을 구현했다. 실제 서비스 프론트 수정과 실제 모델을 사용하는 전체 E2E 검증은 후속 범위다. 엑셀 업로드만으로 등록되는 것은 아니며, 단가표 미리보기 후 등록 권한자의 확인이 필요하다.

## 사용자 흐름

1. 프로젝트 상세 → 문서 기준 → 문서 추가에서 XLSX를 선택한다.
2. 문서 유형 **일정·공수 자료**(`IMPACT_WORKBOOK`)로 등록한다. XLSX는 이 유형으로 자동 분류되며 PDF 계약 문서로 등록할 수 없다.
3. **영향 산정 자료 사용 승인**과 적용일을 지정한다. 미승인 자료는 저장만 한다.
4. 같은 화면의 **영향 산정 자료** 목록에서 확인한다. 계약 기준선 문서 목록과는 별도다.
5. Agent 3 실제 실행 시 승인되고 적용일이 지난 가장 최근 자료 한 개를 직접 읽는다.

형식은 `.xlsx`, 최대 10MB다. `STORED`는 원본 업로드 완료를 뜻하며, 엑셀 내용 검증·일정 계산 완료를 뜻하지 않는다. 내용 오류는 Agent 3가 읽을 때 표시한다.

## 분리 원칙

- 업로드 저장소(S3)는 기존 파일 업로드를 그대로 사용한다. 파일 용도는 `IMPACT_WORKBOOK`이다.
- 문서 버전의 처리 상태는 `STORED`. 색인 이벤트·텍스트 청킹·임베딩·벡터 저장을 실행하지 않는다.
- 계약 기준선에 BASELINE/REFERENCE 어느 역할로도 추가할 수 없다. 계약 근거 수동 청크 등록, 색인 결과 콜백·재시도도 차단한다.
- AI 색인 API도 문서 유형 또는 XLSX MIME으로 잘못 전송된 요청을 임베더 생성 전에 거절한다.
- Agent 2에는 전달하지 않는다. Agent 3 입력의 `operational_schedule`로만 전달하며 계약 범위 근거로 인용하지 않는다.
- AI 일정 파서는 엑셀 **단가표를 직접 계산 입력으로 사용하지 않는다.** 단가 시트는 백엔드 미리보기·확인 등록을 거쳐 프로젝트의 공식 단가표가 된다. 공식 단가·원가·금액은 등록된 UUID와 계산 API로 조회하며 이 시트의 가격을 모델에 보내지 않는다.

## 양식 파일 (기본: WBS·인력 투입 계획, `wbs-v1`)

SI 현장에서 이미 관리하는 자료(주간보고용 WBS, 월별 인력 투입 계획)를 그대로 옮겨 적는 양식이다. 작업별 남은 시간을 따로 적지 않아도 된다.

- 빈 양식: [`data/templates/impact-workbook-template.xlsx`](../../data/templates/impact-workbook-template.xlsx)
- 작성 예시: [`data/templates/impact-workbook-example.xlsx`](../../data/templates/impact-workbook-example.xlsx). 데이터셋 모노마켓(P-COM-101, 계약 9/1~11/23, CO-A-001로 오픈 11/24) 기준 10/12 시점 WBS와 CR-A-009(쿠폰 2장 중복 적용). `예시 결과` 시트의 기대 결과(기존 작업만 11/24 완료, 변경 후 12/02, 일정 영향 6영업일)는 골든 벡터 `monomarket_wbs_coupon_change`(Backend 계산기 실행값)와 같다.
- 두 파일은 `scripts/build_impact_workbooks.py`로 만든다(`openpyxl` 필요, 서버·테스트에는 불필요). 칸 위치·제목 문구를 바꾸면 `app/tools/wbs_workbook.py`와 `tests/test_impact_workbook_template.py`를 함께 확인한다.
- `작성 안내`, `예시 결과`, `단가표` 시트는 AI 일정 파서가 읽지 않는다. 백엔드는 별도 확인 등록 API에서 `단가표`를 읽는다. 파일 업로드만으로 자동 등록하지 않으며 공식 금액은 Backend 등록 단가표로 계산한다.
- 진척률·투입률·담당자 이름·휴무일은 검증용 가정이다. 공휴일은 실제 회사 달력으로 확인한다.

| 시트 | 입력 항목 |
| --- | --- |
| WBS | 진척률 기준일(필수, 일정 계산 시작일), 현재 계획 완료일(선택), 근무 요일. 작업명·담당자·계획 시작/종료일·실적 시작/종료일·진척률·선행 작업·남은 시간(h, 선택)·비고 |
| 인력 투입 계획 | 1 MD 기준 시간(h, 기본 8). 담당자·직군·월별 투입률(`2026-09` 같은 월 열을 빠짐없이) |
| 휴무 | 대상(전체 또는 담당자)·날짜·그날 투입 가능 시간·사유 |
| 단가표 | 적용 시작일·통화·PM/UX/FE/BE/QA별 내부 원가와 판매 단가(1MD 기준)·비고. 1MD 시간은 인력 투입 계획에서 자동 표시 |

양식 화면은 `진행률 기준일`, `진행률`, `실제 시작일·종료일`로 표시한다. 이미 업로드한 양식의 `진척률 기준일`, `진척률`, `실적 시작일·종료일`도 계속 읽는다. 파란 칸은 매주 확인·갱신하는 기준일과 실제 날짜·진행률이며, 노란 칸은 최초 작성·변경 시 수정하는 항목이다. 월 투입률 1.0·0.5는 그 달의 매 근무일에 쓸 수 있는 비율(1MD=8h일 때 8h·4h)이다.

검토용 모노마켓 예시에는 담당자 옆 C열에 `직군`을 자동 표시한다. 담당자 이름으로 `인력 투입 계획`의 직군을 조회하며, 이름이 없거나 직군을 찾지 못하면 `직군 확인`을 표시한다. 이 열은 보기용이며 업로드 시 수식이나 표시값을 계산 입력으로 사용하지 않는다. 공식 직군은 인력 시트에서 읽고, 직군 표시 열이 없는 기존 양식도 계속 지원한다. 오른쪽 간트표는 이동한 날짜 열을 참조하며 기존처럼 작업명과 같은 행에 표시한다. 빈 양식에는 이번 검토용 열을 추가하지 않았다.

인력 시트 2·3행은 투입률과 MM 안내 두 문장만 표시한다. 개인별 `총투입량(MM)`과 `월별 투입규모 합계`는 수식으로 표시하며, 각 달 전체를 기준으로 한 계획 요약이다. 월 중간 참여·휴무를 반영한 실제 시간 또는 변경 견적 금액으로 사용하지 않는다. 파서는 합계 열을 월 열로 읽지 않도록 빈 열로 분리하고, 합계 행부터는 담당자 입력으로 읽지 않는다. 인력 추가는 합계 행 위의 기존 입력 행 사이에 삽입한다. 예시의 김민서(PM)·박서연(UX)·이준호(FE)·최지훈(BE)·정수빈(QA)은 가상 이름이며 WBS·휴무·일정 골든 입력의 이름을 동일하게 맞췄다.

단가표는 기존 입력과 같은 노란 배경·파란 제목 행으로 구성했다. 빈 양식의 가격은 미입력 상태이며 0원으로 채우지 않는다. 예시 단가는 `data/kb/rate_cards.json`의 공통 합성 단가표 `RC-SYNTH-2026H2-v2`이고, 적용 시작일 2026-09-01은 예시용 가정이다. 실제 모노마켓의 DB 단가표를 조회한 값이 아니다. 원가·판매 단가는 선택한 통화 기준의 부가세 제외 금액이다.

등록 연결은 업로드 시 선택한 프로젝트를 대상으로, 직군 코드를 회사의 `jobRoleId`에 매핑하고 관리자 확인 후 기존 `RateCardService`로 새 버전을 등록하는 별도 단계다. `/rate-card-imports/preview`와 `/confirm`을 구현했다. 적용일·통화·1MD 시간·다섯 직군의 단가를 검증하며, 주간 일정 자료 재업로드마다 새 단가표가 자동 생성되지 않는다. 엑셀의 단가를 바꾸기만 해서는 반영되지 않고, 확인 등록 후 유효 단가표로 재산정해야 공식 금액과 문안이 갱신된다.

변환 규칙:

- 실적 시작·종료일은 진척률 기준일 이후일 수 없으며 실적 종료일은 시작일보다 빠를 수 없다. 진척률 100% 또는 유효한 실적 종료일이 있는 작업은 완료로 처리하고 선행 작업에서도 지운다. 실적 종료일이 있는데 100%가 아니면 거절한다.
- 남은 시간은 `남은 시간(h)`을 적으면 그 값, 없으면 `계획 기간의 담당자 투입 가능 시간 × (1 − 진척률)`을 0.5시간 단위로 올린다. 투입 가능 시간은 아래 하루 투입 시간을 근무요일·휴무에 맞춰 더한 값이다.
- 소수 계산은 Decimal로 처리한 뒤 마지막에 한 번 올린다. 예: 20h × (1 − 95%) = **1h**. 직접 입력한 0h는 추정값으로 바꾸지 않는다.
- 같은 담당자의 미완료 작업 계획 기간이 겹치면 가용시간을 각 작업에 중복 적용하지 않는다. 겹치는 작업 중 진척률 추정을 쓰는 작업은 남은 시간을 직접 입력해야 한다. 작업별로 직접 입력한 공수는 그대로 사용한다.
- 하루 투입 시간 = 그 달 투입률 × 1 MD 기준 시간. 표 마지막 달 이후에는 마지막 달 투입률이 이어진다고 본다. 일정 계산 요청을 만들 때 마지막 달 값을 담당자 기본 시간으로, 달마다 다른 값은 담당자별 예외 근무일로 펼친다(`wbs_workbook.expand_staffing`). Backend 계산기는 바뀌지 않았다.
- 현재 계획 완료일을 비우면 남은 작업의 가장 늦은 계획 종료일을 쓴다.
- 진척률·투입률은 `70%` 또는 `0.7`처럼 입력한다. 단위 없는 `70` 및 100% 초과는 거절하며 자동 축소하지 않는다. 월 열 제목은 `2026-09`, `2026년 9월`, Excel이 날짜로 바꾼 값 모두 받는다. 월 열은 C열부터 첫 빈 칸 전까지다.
- 엑셀의 1 MD 기준 시간은 백엔드 공식 금액 계산의 기준과 일치해야 한다. 다르면 금액 기준을 바꾸지 않고 일정만 미산정으로 남기며 사유를 표시한다. 개인별 가용시간은 월 투입률로 조절한다.
- 추정·가정은 `assumptions`로 결과(`impact_workbook.data`, `plan_detail.assumptions`)에 남고, 고객 문서 일정 사실에 "WBS 진척률 기준 추정" 문구가 붙는다.
- 계산기는 계획 시작일을 지키지 않는다. 선행 작업이 끝나고 담당자 시간이 비면 바로 시작한다고 본다.

기본 모노마켓 예시는 검수 공수 20h인 합성 사례다. 별도 골든 사례 `monomarket_wbs_coupon_existing_delay`는 원래 검수 공수 28h를 유지한다. 기존 작업 완료 11/26 → 변경 후 12/04이며 계획 완료일 11/24 대비 전체 지연은 8영업일, 변경 요청으로 추가된 영향은 6영업일이다. 기존 지연을 제거하려고 원래 공수·기간을 수정하지 않는다.

자주 틀리는 것:

- 변경 요청으로 새로 생길 작업은 적지 않는다. Agent 3가 만든다.
- `선행 작업`에는 WBS의 작업명만 적는다. `확인 필요` 같은 표에 없는 값은 파일 전체를 거절한다.
- 끝나지 않은 작업의 담당자는 모두 `인력 투입 계획`에 있어야 한다.
- 휴무 표의 사유만 적고 대상을 비운 행은 오류다.
- Agent 3는 엑셀의 담당자·작업 이름을 그대로 써서 새 작업을 배치한다. 이름이 맞지 않는 작업 행이 하나라도 있으면 일정을 계산하지 않는다.

## 간소화 양식 (기존, 계속 지원)

시트 이름이 `WBS`가 아니고 `기존 작업`·`사람과 근무일`이면 아래 양식으로 읽는다. 이미 올린 자료와 테스트를 위해 유지하며 새 양식 파일은 제공하지 않는다.

| 시트 | 입력 항목 | 처리 |
| --- | --- | --- |
| 기존 작업 | 일정 계산 시작일, 현재 계획 완료일(선택), 작업명·담당자·남은 시간(h)·선행 작업명 | 기존 작업은 신규 요청의 추가 공수에 합산하지 않음 |
| 사람과 근무일 | 근무요일, 담당자·하루 투입 가능시간(h)·투입 가능일(선택), 예외 근무일 | 시작일 생략은 프로젝트 계산 시작일 사용. 하루 0~24시간 |
| 단가표 | 등록 단가 조회용 | 공식 계산 입력으로 사용하지 않음 |

## 공통 검증

선행 작업은 작업명을 세미콜론으로 구분한다. 중복 작업명·담당자, 알 수 없는 담당자/선행 작업, 순환 선행관계, 음수/누락 공수, 외부 연결·매크로·입력 수식은 거절한다. 요약 합계 수식은 실행하지 않는다. 작업·인력은 각각 200행, 휴무·예외 근무일은 1000행까지 지원한다. 빈 문자열 칸(`<is>` 없는 inlineStr)은 빈 값으로 읽는다.

정해진 양식만 지원한다. 임의의 WBS 엑셀을 자동 추론해 받아들이지는 않는다. 계획 완료일이 없으면 지연 폭을 미산정으로 남긴다. 휴무 빈칸도 실제 휴무 없음 확정을 뜻하지 않는다.

## 연결 계약

- Backend: `GET /internal/v1/projects/{projectId}/impact-workbook`
- 인증: 기존 `X-Internal-Token`. 새 시크릿 불필요.
- 반환: `{ "workbook": null }` 또는 원본 정보(projectId, documentId, documentVersionId, version, title, objectKey, sha256, mimeType, sizeBytes).
- 선택: `IMPACT_WORKBOOK + APPROVED + STORED + 적용일 <= 오늘(미입력은 즉시)` 중 등록 시점 최신 1개. 새 버전이 미승인/미래 적용이면 이전 유효 승인 버전을 계속 사용한다.
- AI는 지정된 `S3_SOURCE_BUCKET`에서 objectKey 원본을 크기 제한 내 읽고, 파일 크기·SHA-256을 확인한다. Backend S3 버킷과 같은 저장소를 가리켜야 한다.
- 자료 없음은 기존 분석 흐름을 유지한다. 조회/저장소 장애는 자료 없음으로 숨기지 않고 실패로 표시한다. 합성 프로젝트는 조회하지 않는다.
- `impact_workbook.source`에 버전·해시, `data`에 구조화 입력을 결과에 고정한다. Run payload에서도 보존한다.
- 사용 자료 교체·승인 철회·적용일 변경으로 현재 원본이 달라지면 AI 검토·문서 생성과 Backend 최종 산정 대조에서 재산정을 요구한다. 기존 문서·승인을 그대로 재사용하지 않는다.

## 적용과 검증 범위

문서 유형·파일 용도·처리 상태의 허용값은 Backend Flyway `V5__estimate_calculation_snapshot_and_impact_workbook.sql`이 맞춘다. V1 기준과 같도록 세 컬럼의 값 목록 CHECK를 제거하고 허용값은 애플리케이션 enum이 검사한다. 앱 기동 시 자동 적용되며 수동 DDL은 필요 없다.

Frontend·Backend·AI를 함께 재시작해야 새 유형과 내부 조회 경로가 반영된다. 새 환경변수나 Jira 연결은 필요 없다. 실제 UUID 프로젝트는 Backend 조회 경로가 준비되어 있어야 한다.

이번 범위: 업로드·격리·승인 자료 선택·구조화 파싱·Agent 3 컨텍스트·버전 보호.
후속 범위: 엑셀 입력 즉시 미리보기/오류 검증, Jira/Git 동기화, PM 공수 수정 뒤 일정 자동 재계산(지금은 비우고 재산정 안내).
