# 일정 계산기 (schedule-v1)

작성일: 2026-11-20. 계산식 v1의 38~41번(선행 조건, 시작 가능일, 예상 완료일, 일정 영향)을 계산한다. 37번(소요 영업일)·42번(남은 영업일)은 기존 금액 계산 응답의 `schedule_detail`에 그대로 있다.

## 흐름

1. PM이 일정·공수 엑셀(`IMPACT_WORKBOOK`)을 올리고 승인한다. 양식은 [impact-workbook-upload.md](impact-workbook-upload.md).
2. Agent 3가 작업 행마다 일정 배치를 **제안**한다. 날짜·기간은 쓰지 않는다.
   - 새 작업: `assignee`(엑셀 담당자 이름), `after`(먼저 끝나야 하는 기존 작업), `before`(이 작업 뒤에 할 기존 작업)
   - 기존 작업 시간 증가(재작업·추가 테스트): `extends_task`(기존 작업 이름). 담당자는 그 작업의 담당자
3. AI(`app/tools/schedule_plan.py`)가 엑셀 이름과 대조해 입력을 만든다. 맞지 않는 행이 하나라도 있으면 계산하지 않는다(`plan_detail.plan=null`, `unassigned`에 행별 사유).
4. Backend `POST /internal/v1/estimates/schedules`가 기존 계획과 변경 후 계획을 모두 배정하고 완료일·일정 영향을 돌려준다. 입력 전체와 해시를 `snapshot`에 담는다.
5. 최종 승인 때 `POST /internal/v1/estimates/schedules/validations`로 저장된 결과가 같은 입력으로 재현되는지 확인한다. 바뀌었으면 승인하지 않는다.

계산 공식은 Backend에만 있다. AI는 입력 변환과 표시만 한다. 계산기 장애는 다른 값으로 대체하지 않고 사유로 남긴다.

## 계산 규칙

| 항목 | 규칙 |
|---|---|
| 선행 조건(38) | 선행 작업이 모두 끝난 날의 **다음 근무일**부터 시작. 당일 이어받기·분할 병렬화 없음 |
| 시작 가능일(39) | 일정 계산 시작일, 담당자 투입 가능일, 선행 조건 중 가장 늦은 날 이후 담당자 시간이 남는 첫 날 |
| 배정 | 남은 시간을 담당자의 하루 가용 시간 안에서 날짜 순으로 채운다. 같은 담당자의 같은 날 시간은 여러 작업이 나눠 쓰고 초과하지 않는다 |
| 처리 순서 | 선행 관계를 지키는 범위에서 입력 순서(엑셀 기존 작업 → 새 작업) |
| 예상 완료일(40) | 변경 후 계획에서 가장 늦게 끝나는 작업의 날짜 |
| 일정 영향(41) | 현재 계획 완료일 다음 날부터 변경 후 완료일까지의 영업일. 일찍 끝나면 0. 계획 완료일이 없으면 null |
| 참고값 | `impact_vs_baseline_business_days`: 같은 엑셀로 계산한 기존 완료일 대비 늘어난 영업일. 계획 완료일이 없어도 계산된다 |
| 근무일 | 근무 요일이면서 전체 휴무가 아닌 날. 예외 근무일은 그 날 그 사람(또는 전체)의 시간을 덮어쓴다(0이면 휴무) |
| 0시간 작업 | 기간을 차지하지 않고 선행 작업이 끝난 날에 끝난 것으로 본다 |

검증(입력을 고치지 않고 거부): 모르는 담당자·선행 작업, 순환, 음수 시간, 중복 ID, 1,100일 안에 배정 불가(가용 시간 0 등), 변경 작업 시간 합계 ≠ 금액 계산의 총 시간.

## 결과 필드 (`plan_detail`)

| 필드 | 뜻 |
|---|---|
| `plan.baseline`, `plan.changed` | 기존·변경 후 계획: 완료일(`end`), 작업별 시작·완료일, 날짜별 배정 |
| `plan.change_start_date` | 새로 생기거나 늘어난 작업 중 가장 이른 시작일 |
| `plan.estimated_end_date` | 변경 후 예상 완료일(40) |
| `plan.impact_business_days` | 일정 영향(41) |
| `plan.change_hours` | 변경으로 늘어난 총 시간 = 금액 계산의 `total_hours` |
| `plan.snapshot` | 입력 전체, `input_hash`, `snapshot_id`, `calculated_at` |
| `unavailable_reason`, `unassigned` | 계산하지 않은 사유와 행별 미배정 사유 |

기존 `Schedule.business_days`는 바꾸지 않는다. 계산된 일정이 있으면 최종 승인 때 "일정 미산정 확인"을 요구하지 않는다.

## 알려진 한계

- 결과는 엑셀에 적힌 남은 시간·가용 시간·선행 관계를 전제로 한 **가정 일정**이다. 엑셀이 실제와 다르면 결과도 다르다.
- 담당자·선행 관계는 모델 제안이다. 근거가 없으면 비워 두도록 했고, 비면 계산하지 않는다. PM이 담당자를 직접 고치는 화면은 없다.
- PM이 공수를 수정하면 Backend는 금액만 다시 계산하고 일정은 비운 뒤 재산정을 안내한다(담당자 제안이 DB 산정 라인에 없음).
- 고객 희망 납기(`client_requested_deadline`) 충족 여부는 판단하지 않는다.

## 검증

- Backend `ScheduleV1GoldenTest`: 샘플 기대값(완료일 12/1, 일정 영향 2영업일)과 추가 사례 4건, 오류 사례 10건, 모든 사례의 가용 시간·근무일·선행 조건 불변식.
- AI `tests/test_schedule_plan.py`: 엑셀 형태 입력이 Backend 골든 입력과 같게 변환되는지, 미배정·장애·문서 표시. `tests/test_agent3_orchestration.py`: 모델 제안 → 일정 계산 → 문서 → 승인 시 재검증, 결과 변조 시 승인 거부.
- 두 저장소의 골든 파일은 같은 파일이며 AI 테스트가 바이트 단위로 비교한다.
