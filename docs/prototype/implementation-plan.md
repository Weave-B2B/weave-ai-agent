# 변경요청 확인용 UI — 첫 구현 범위 제안

작성일: 2026-10-28 / Asia/Seoul. 상태: **B 혼합안 선택 및 화면 구현 착수 승인**.
근거: [기획 준비도](readiness.md), [자료 출처 지도](source-map.md), [현재 Agent 3 계약](../agent3-mvp.md).
개인 개발팀은 이번 프로젝트의 기존 소유권을 따르며, 서비스 백엔드·DB·인프라 설계를 새로 맡지 않는다.

사용자 직접 답변 **“추천안으로 화면 구현 시작”**에 따라 B안을 이번 구현 범위로 확정한다.
아래 A/C는 선택을 위해 검토한 대안의 기록이며, 현재 사용자 답변을 다시 요구하는 선택지가 아니다.

## 확정 범위와 검토한 대안

| 안 | 화면과 동작 | 실제 연결 | 얻는 결과 |
|---|---|---|---|
| A. 화면 흐름 먼저 | C02 목록 → C03 원문 → C04 범위 → C05 산정 → C06 초안의 선택된 상태 | 명시적인 mock adapter. 제품 API/LLM 호출 없음 | Figma 메뉴 이동·표·버튼·상태를 먼저 눈으로 검토 |
| **B. 변경요청 흐름 + Agent 3 API (권장)** | C02~C04는 샘플 조회, C05 산정/수정/승인·반려, C06 내부 초안 | C05/C06은 기존 `/agent3` 네 API. 상위 입력은 합성 fixture | 화면 맥락과 실제 A3 상태 전이를 함께 확인 |
| C. Agent 3 핵심 화면만 | C05와 C06 내부 초안만 먼저 구현. 합성 입력을 선택해 실행 | 기존 `/agent3` 네 API | 가장 작은 화면 범위로 산정→수정→승인→초안 확인 |

확정안은 **B**다. 이후 A/C로 범위를 변경할 필요가 생기면 매니저가 사용자에게 이유와 변경 범위를 제시한다.
어느 안이든 전체 변경요청 관리 서비스·고객 협의 운영·청구·실제 사용자 인증·영속 저장을 포함하지 않는다.

**API 연결과 실제 모델 추론은 별개다.** B/C도 처음에는 서버의 fake 모델 응답으로 코드 계산·수정·승인 상태를 검증할 수 있다.
이 경우 UI에 `API 연결 / 모델: 가상 응답 / 상위 입력: 합성 fixture`를 구분해 표시한다.
실제 외부 모델 연결은 현재 미승인이다. 설정과 검증 범위를 확인한 뒤 별도 선택한다.

## 화면별 허용 범위 — B 선택 시 제안

| 화면 | 이번에 동작하게 할 것 | 이번에 실제로 구현하지 않는 것 |
|---|---|---|
| C02 Inbox | 합성 요청 목록, 검색·상태 필터, 상세 이동, mock/API 모드 구분 | CN 전체 요청 CRUD·실제 수신 채널·내보내기 업무 API |
| C03 요청 원문 | 합성 원문·항목·근거·질문 조회. 상위 입력 출처 설명 | A1/A2 실제 재분석·질문 답변 영속 저장·첨부 업로드 |
| C04 범위 검토 | 합성 PM 판단과 `estimate=true` 선택 근거 조회, 산정 화면 이동 | 실제 PM 범위 확정 API·공유 상태 엔진 변경 |
| C05 영향 산정 | 산정 실행, 작업/직군/MD·가정·합계·미산정 사유, 공수 수정/재계산, PM 승인·반려 | 새 단가 조회·독립 가격/일정 수정 API, 실제 PM 인증 |
| C06 승인·협의 | 유효한 PM 승인 후 반환된 내부 초안 조회·복사 또는 기존 형식 저장 | 고객 발송·상업 승인·고객 승인·청구·새 버전 관리 API |

Figma의 C07 실행·검수 및 등록/근거/버전비교/전체이력 보조 화면은 첫 기본 범위에서 제외하는 제안이다.
보조 UI가 꼭 필요한 경우 사용자에게 범위를 다시 제시하며, 기능이 없는 버튼은 동작 완료로 꾸미지 않는다.

## 최소 API 연결 계약 — B/C 공통

| 사용자 행동 | 기존 API | 화면의 처리 |
|---|---|---|
| 산정 실행 | `POST /agent3/impacts` | 승인된 합성 `Agent3Input`을 전송하고 반환한 세션·버전·결과·해시를 현재 상태로 보관 |
| 현재 상태 확인 | `GET /agent3/impacts/{session_id}` | 산정·승인·초안·history를 표시. 없는 세션은 새 시작을 안내 |
| 공수·가정 수정 | `POST /agent3/impacts/{session_id}/edit` | 최신 `state_revision`, `target_result_id`, `estimates`, `reason` 전송. 응답의 새 결과/금액·승인 무효화를 반영 |
| PM 승인·반려 | `POST /agent3/impacts/{session_id}/review` | 최신 revision/result/hash와 요청 ID·검토자 참조·결정 전송. 미산정 인지 및 반려 사유 규칙 유지 |

`estimates` 수정은 현재 item 그룹을 유지하고 MD는 유한한 0 이상·0.5 단위를 따른다.
금액은 응답의 `calc_cost` 합계를 표시하며 UI 임의 견적을 실제 계산 결과로 쓰지 않는다.
단가·행별 금액처럼 현재 응답에 없는 값은 `API 미제공`으로 명시하거나 화면에서 제외한다.
합성 단가를 참고값으로 보여줄 필요가 있다면 실제 API 값과 분리하는 표시를 먼저 합의한다.

브라우저→기존 API의 로컬 실행 방식은 화면 담당이 현재 서버 설정을 확인해 최소로 제안한다.
같은 origin의 정적 화면 제공 또는 로컬 개발 연결에 필요한 설정을 검토할 수 있지만,
이를 이유로 새 업무 API·인증 서버·DB를 만들지 않는다. 코드 변경 경로가 추가되면 착수 범위에 포함해 승인받는다.

A안에서는 API 코드가 실행됐다고 보고하지 않는다. 모의 응답으로 같은 상태별 화면을 확인한다.
B/C안에서는 실제 API 호출·응답과 UI 상태를 확인하되, fake 모델 검증을 실제 모델 품질 검증으로 보고하지 않는다.

## 반복 실행과 검증 준비

- 현재 API 설명상 fake 응답 파일은 한 건이다. `POST /impacts`로 모델 산정을 반복하려면
  테스트 응답 배열·프로세스 재시작 또는 별도 합의된 실행 설정이 필요할 수 있다.
  프론트엔드만으로 모델 응답 반복이 해결됐다고 간주하지 않는다.
- 공수 수정·승인·초안 작성은 추가 모델 호출 없이 기존 워크플로가 처리한다.
- API 모델 장애 등 실제로 재현하기 어려운 UI 상태는 분리된 mock adapter/네트워크 모의 조건에서 검증하고,
  실제 API 연결의 증거와 구분한다.
- 사용자가 위 B안의 화면 구현 시작을 승인했다. 화면 담당이 승인된 목표를 위한 코드와 최소 로컬 서빙 구성을 검토한다.
  새 업무 API·공유 스키마·DB·인프라 변경은 승인 범위가 아니다.
- 별도 QA 담당은 아직 착수 미승인이다. 구현 결과를 받은 뒤 매니저가 검증 범위와 착수를 사용자에게 제시한다.
  승인된 QA는 브라우저 흐름과 관련 API/회귀 검사를 실행하고 실제 결과만 기록한다.

## 다음 담당자 인수인계

1. **화면 설계/구현 담당 — 착수 승인됨:** B안 C02~C06의 현재 Figma를 필요한 만큼 확인하고 `prototype/` 중심으로 구현한다.
   기존 API를 호출하기 위한 최소 로컬 서빙 방식은 현재 서버 설정을 읽어 정한다. 작은 구현 선택마다 재확인하지 않는다.
2. **유지할 계약:** C02~C04 fixture, C05/C06 기존 API; 단가·행별 금액 API 미제공 표시;
   직접 금액/일정 편집 제외; 미산정과 PM 승인·재승인 유지; 고객 승인·발송·청구 제외.
3. **실행 준비:** fake 모델의 초기 응답 한 건 제한을 확인하고 반복 산정 방법을 구분한다.
   실제 모델 추론이나 운영 DB 연결이 완료됐다고 보고하지 않는다.
4. **QA 담당 — 착수 대기:** 구현 결과와 위 수용 기준을 받은 뒤 사용자 착수 승인 범위에서 검증한다.
   수정·재검증은 승인 범위 내에서 기본 최대 두 회다.

이 문서는 기획 충분성 검토 결과이며 제품 화면 구현 완료나 QA 통과 보고가 아니다.
